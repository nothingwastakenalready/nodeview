# raffael v0.2 design

## why

v0.1 is useful from a terminal. v0.2 should be useful as a thing that stays running.

raffael is now intended to grow into a real self-hosted monitoring platform, but v0.2 deliberately does not try to build that whole platform at once. keep the existing checks, put a small HTTP interface in front of them, and make the first server layer boring to run in docker.

The long-term direction is documented in `docs/architecture/product-vision.md` and `docs/architecture/roadmap.md`. v0.2 is the first server-side slice of that architecture.

## shape

```text
services.yaml
     |
     v
 config loader
     |
     v
 check dispatcher ---- http check
     |              `-- tcp check
     v
 current results
   |       |
   cli     api
            |
            +-- GET /health
            +-- GET /services
            `-- POST /check
```

The CLI and API use the same config/check code. No second implementation hiding in the web layer.

## api

FastAPI, because writing our own HTTP plumbing here would mostly prove that sockets exist.

`GET /health`

Returns whether raffael itself is alive. It does not run service checks.

```json
{"status":"ok"}
```

`GET /services`

Loads the configured services and runs the same HTTP/TCP checks the CLI already uses. Returns JSON results.

```json
[
  {"name":"example","type":"http","status":"up","latency_ms":41,"http_status":200,"error":null},
  {"name":"ssh","type":"tcp","status":"up","latency_ms":7,"http_status":null,"error":null}
]
```

`POST /check`

Runs one ad-hoc check from a service definition in the request body. Useful later for a web UI without making config mutation part of v0.2.

No auth yet. That means this is for a trusted/private network in v0.2, not something to dump naked onto the internet.

## config

The API reads a config path from `RAFFAEL_CONFIG`, defaulting to `/config/services.yaml` in the container. Local CLI behavior stays compatible.

No database. No config editor. No state persistence.

## docker

One small Python image. `compose.yaml` mounts `./services.yaml` read-only into `/config/services.yaml` and publishes port 8080.

Container command runs uvicorn. The existing CLI still works outside the container and can also be invoked inside it if someone really wants to.

## tests

API behavior is tested through FastAPI's test client with check functions isolated where needed. Existing config, HTTP, TCP and CLI tests stay green.

CI keeps Python 3.11/3.12 and now covers the API tests too. Docker build is verified separately so a passing Python suite cannot hide a broken image.

## not v0.2

These are planned later, not rejected from the product:

- web dashboard
- prometheus
- auth/workspaces
- database/history
- config writes
- scheduler
- notifications
- agents
- dependency graph
- desktop app
- kubernetes, obviously

## done when

- `/health`, `/services` and `/check` work
- HTTP and TCP results use one shared dispatcher
- `docker compose up -d` starts the API with a mounted config
- tests are green on 3.11 and 3.12
- docker image builds in CI
- README explains the new path without turning into documentation cosplay
