# Raffael v0.4 measurement history design

## goal

Give Raffael its first durable monitoring history so the product can answer what changed without inventing frontend data.

This slice also completes the product rename from Raffael to Raffael across the repository, package, API and current UI copy. The visual redesign and logo remain separate design work.

## scope

- rename the Python package and product-facing copy to `raffael`
- introduce SQLAlchemy 2.x as the persistence boundary
- store one immutable measurement after every scheduled check result
- store timestamps in UTC
- provide a bounded, time-range history API for one configured service
- include an initial Alembic migration
- keep SQLite as the default local database path
- add a persistent Compose data volume

## non-goals

- no uptime aggregation yet
- no retention job yet
- no state-change event table yet
- no workspace, node or authentication model
- no historical graph until the API is backed by real measurements
- no logo or final visual identity in this slice

## data model

`measurement`

- integer primary key
- service name
- resulting state (`up`, `warning`, `critical`, `unknown`)
- latency in milliseconds, nullable
- HTTP status, nullable
- error text, nullable
- UTC check timestamp

Measurements are append-only. Current in-memory state remains the fast operational snapshot; history is a separate concern.

## runtime flow

1. The monitoring engine executes a configured check.
2. Existing threshold logic derives the current service state.
3. The new state replaces the in-memory snapshot.
4. The resulting measurement is written through a narrow repository interface.
5. `GET /history/{service_name}` queries the repository with optional `from`, `to` and bounded `limit` parameters.

Persistence failures must not fabricate healthy data. They are allowed to surface from `run_once` in this first slice so operators and tests can observe broken storage rather than silently losing history.

## security and growth boundaries

- SQLAlchemy parameterizes service names and timestamps.
- history responses are capped at 1,000 rows.
- the database remains local to the trusted self-hosted deployment.
- no new network exposure or target policy is introduced.
- retention and tenant authorization remain required before hosted use.

## verification

- repository round-trip and time-range tests
- engine recording tests
- API history tests, including limits and validation
- full Python suite
- frontend tests and production build
- clean-database Alembic upgrade
