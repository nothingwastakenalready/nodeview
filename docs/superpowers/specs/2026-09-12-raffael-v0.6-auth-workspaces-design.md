# Raffael v0.6 — local accounts and workspace boundary

## status

Proposed. This slice establishes the backend security boundary before the
dashboard is connected to real authentication.

## goal

Provide a small, reviewable local-account foundation for self-hosted Raffael:
users can register, sign in, inspect their session, and sign out. A user owns
or joins a workspace through an explicit membership. Workspace identity is
resolved server-side from the session and membership, never trusted from a
client-supplied object identifier.

## scope

- users with normalized email addresses and Argon2id password hashes
- workspaces and memberships with owner/admin/member/viewer roles
- opaque, server-side sessions stored as SHA-256 token hashes
- session rotation on login and revocation on logout
- Secure/HttpOnly/SameSite cookies, with local-development configuration
- CSRF token endpoint and double-submit validation for cookie-authenticated
  state-changing requests
- registration, login, current-session and logout endpoints
- migration and focused unit/integration/security tests

## non-goals

- OIDC/OAuth, 2FA, invitations, password reset and email delivery
- full workspace administration UI
- changing the existing YAML monitor configuration into workspace data
- internet-facing deployment recommendation

## security decisions

- Passwords are never stored or logged; Argon2id is the only accepted password
  representation.
- Raw session tokens exist only in the browser cookie and are hashed at rest.
- Login responses do not reveal whether an email exists.
- Session IDs rotate on successful login.
- Authentication cookies are HttpOnly and SameSite=Lax by default; Secure is
  enabled in production configuration.
- Mutating cookie-authenticated requests require a CSRF token.
- Workspace access requires an active membership and is covered by explicit
  cross-workspace regression tests.

## acceptance criteria

- fresh database migration succeeds
- registration creates exactly one user, workspace and owner membership
- duplicate email registration is rejected without disclosing account details
- login creates a new session and never returns the raw session token in JSON
- logout revokes the session
- expired, revoked and cross-workspace sessions cannot access protected data
- all existing monitoring and history tests remain green
- documentation states the deployment/security limits honestly
