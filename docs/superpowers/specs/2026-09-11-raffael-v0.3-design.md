# raffael v0.3 design

## why

v0.2 can answer when something asks it to check.
v0.3 should keep checking by itself and expose a stable current state.

This is the first monitoring-engine slice. No database yet. No history yet. No UI yet.

## goals

- continuously execute configured checks
- bounded concurrency
- deterministic current state per configured service
- configurable interval and state thresholds
- avoid single-sample flapping
- graceful startup/shutdown
- keep HTTP/TCP checker code reusable and unchanged in purpose

## config additions

Each service gets optional monitoring fields:

```yaml
services:
  - name: example
    url: https://example.com
    interval: 30
    failure_threshold: 2
    success_threshold: 1
```

Defaults:

- `interval`: 30 seconds
- `failure_threshold`: 2
- `success_threshold`: 1

Validation:

- interval > 0
- thresholds >= 1

Existing v0.2 configs remain valid.

## state model

A service begins as `pending`.

Internal current-state record:

- service name
- status: `pending | up | warning | critical | unknown`
- last latency
- last HTTP status when relevant
- last error
- last checked timestamp
- consecutive successes
- consecutive failures

State semantics for v0.3:

- `pending`: no completed sample yet
- `up`: latest successful check and success threshold satisfied
- `warning`: failure observed, but failure threshold not yet reached
- `critical`: failure threshold reached
- `unknown`: checker crashed or produced an unexpected engine-level error

A success resets consecutive failures. A failure resets consecutive successes.

Recovery from warning/critical requires `success_threshold` consecutive successes. Until that threshold is met, the previous non-up state remains.

This intentionally separates the raw check result (`up/down`) from monitoring state (`up/warning/critical/...`).

## scheduler

Use `asyncio` in-process. No external scheduler dependency.

The scheduler owns one loop per configured service and one shared semaphore for bounded concurrency.

Conceptually:

```text
config
  |
  v
MonitoringEngine
  |-- state store
  |-- asyncio task: service A --\
  |-- asyncio task: service B ----> semaphore --> check_service
  `-- asyncio task: service C --/
```

Synchronous network checks run through `asyncio.to_thread()` so they do not block the event loop.

Initial maximum concurrency: configurable constructor argument, default 10.

Scheduling rule: run immediately on startup, then sleep for the service interval after each completed run. v0.3 does not attempt fixed-wall-clock scheduling or compensate for check duration.

## engine interface

Create `src/raffael/engine.py`.

Primary types/functions:

- `ServiceState`
- `apply_result(previous, result, service, checked_at)`
- `apply_error(previous, service, error, checked_at)`
- `MonitoringEngine(services, checker=check_service, max_concurrency=10)`
- `await engine.start()`
- `await engine.stop()`
- `engine.states()` returns an immutable/safe snapshot mapping service name to state
- `await engine.run_once(service)` for deterministic tests and future API integration

`start()` must be idempotent enough not to duplicate scheduler tasks when called twice.
`stop()` cancels and awaits service tasks cleanly.

## API integration

v0.3 does not replace `/services` behavior with scheduler state yet. The engine is introduced as a tested subsystem first.

Add a new `GET /state` endpoint backed by an engine injected into `create_app` when present. If no engine is provided, `/state` is not required to be registered.

The default module-level app should create/start one engine using FastAPI lifespan and configured services. This makes the container actually monitor continuously.

`GET /health` remains process health, not monitored-service health.

## timestamps

Use timezone-aware UTC `datetime` values internally and serialize ISO-8601 through FastAPI/Pydantic-compatible data.

## failure boundaries

A normal protocol/network failure is already a `CheckResult(status="down")` and feeds warning/critical thresholds.

An exception escaping `checker(service)` is different: engine state becomes `unknown`, the scheduler survives, and the error is captured as text. One broken checker must not kill its scheduling loop.

## tests

Test pure state transitions separately from timing/scheduler behavior.

Required coverage:

- initial pending state
- first success -> up with default threshold
- first failure -> warning when threshold is 2
- second consecutive failure -> critical
- success resets failure counter
- configured success threshold delays recovery
- checker exception -> unknown
- `run_once` updates state
- scheduler starts checks automatically
- bounded concurrency is respected
- stop cancels scheduler tasks cleanly
- config parses defaults and custom interval/thresholds
- existing v0.2 tests remain green

Timing tests should use short intervals and events/counters, not long sleeps.

## not v0.3

- SQL/database
- history/measurements retention
- uptime calculation
- alerting
- DNS/ICMP checks
- workspaces/auth
- UI
- distributed scheduler
- cron syntax

## security impact

No new trust boundary and no internet-facing auth claim.

However, continuous scheduling amplifies SSRF/egress risk because configured targets are now contacted repeatedly. v0.3 remains explicitly trusted/self-hosted. Target-policy hardening is required before untrusted multi-user use.

## done when

- configured services begin monitoring automatically when the API starts
- current state survives checker failures without killing the engine
- state thresholds behave deterministically
- checks do not block the event loop
- concurrency is bounded
- shutdown is clean
- API can expose current state
- all Python 3.11/3.12 tests and Docker build are green
